## Criterios de aceptación

| ID | Criterio |
|---|---|
| CA-01 | Un visitante se registra como cliente desde el acceso de artistas con nombre, teléfono, nombre artístico, correo y contraseña; su perfil queda con rol `cliente` y esos datos. |
| CA-02 | Supabase Auth rechaza contraseñas de menos de 8 caracteres o sin minúscula, mayúscula, número y símbolo. El formulario muestra un medidor con las cuatro condiciones (cada una con marca y texto, no solo color) y el nivel en texto: débil, media o fuerte. |
| CA-03 | El cliente inicia sesión con correo y contraseña; un error no revela si el correo existe ("Correo o contraseña incorrectos"). |
| CA-04 | El acceso de artistas ofrece "Continuar con Google" y "Continuar con Facebook" (proveedores de Supabase Auth de una lista configurable, [ADR-009](../00-proyecto/decisiones/ADR-009-reservas-tarifas-y-caducidad.md)), cada uno solo si está configurado; el acceso interno nunca los ofrece. |
| CA-05 | "¿Olvidaste tu contraseña?" envía un enlace de restablecimiento (en local, visible en Mailpit) con la misma respuesta exista o no el correo; la nueva contraseña cumple CA-02. |
| CA-06 | El cliente puede iniciar sesión y reservar sin verificar el correo; el perfil indica `correo_confirmado`. Desde el perfil pide "Verificar mi correo" y recibe un enlace de un solo uso (en local, en Mailpit); al abrirlo, el backend registra la verificación. RF-05 la exige antes del primer pago. Quien entra con Google queda verificado. |
| CA-07 | Desde el registro interno, una persona crea su cuenta y una solicitud de acceso con su especialidad; mientras está pendiente no entra al panel interno y ve el estado de su solicitud. |
| CA-08 | El Administrador ve las solicitudes pendientes, aprueba (asigna rol `personal` o `administrador` y especialidad) o rechaza con motivo. La persona aprobada entra al panel; la rechazada ve el motivo. |
| CA-09 | Cada usuario edita su nombre y teléfono, y el cliente su nombre artístico. Nadie cambia su propio rol ni especialidad, ni el perfil de otro (la fila ajena queda intacta). |
| CA-10 | El Administrador cambia rol y especialidad de cualquier usuario; no puede dejar el sistema sin administradores (quitarse el rol siendo el último → 409). |
| CA-11 | El primer Administrador se crea con `uv run python -m bugalu.herramientas.crear_administrador <correo>` sobre un usuario ya registrado. |
| CA-12 | Cerrar sesión elimina la sesión del navegador y vuelve al acceso. |
| CA-13 | Casos de rotura: token manipulado o caducado → 401; servicio de claves o base caídos → 503; `anon` y otros usuarios no leen ni cambian lo ajeno; las islas muestran su estado ante 401, 403, 503, red caída y respuesta no JSON; todo funciona o se explica sin JavaScript. |

## Contrato API

Base `/api/v1`. Autenticación por `Authorization: Bearer <token de Supabase>`. Errores con el formato único ([convenciones](../01-arquitectura/convenciones.md#api)). Registro, inicio de sesión, Google, recuperación y cierre de sesión van directamente contra Supabase Auth desde el navegador, no por esta API.

| Método y ruta | Acceso | Cuerpo | Respuesta | Errores |
|---|---|---|---|---|
| `GET /perfil` | autenticado | — | 200 `Perfil` | 401, 404 `perfil_no_encontrado`, 503 |
| `POST /perfil/verificar-correo` | autenticado con sesión abierta por enlace de correo o por Google | — | 200 `Perfil` (`correo_confirmado: true`) | 401, 409 `verificacion_no_valida` (la sesión no viene de un enlace de correo ni de Google) |
| `PATCH /perfil` | autenticado | `{nombre?, telefono?, nombre_artistico?}` | 200 `Perfil` | 401, 422 `datos_invalidos`, 422 `campo_no_permitido` (`nombre_artistico` si no es cliente) |
| `POST /solicitudes-acceso` | autenticado | `{especialidad, mensaje?}` | 201 `Solicitud` | 401, 409 `conflicto` (ya tiene una pendiente o ya es personal), 422 |
| `GET /solicitudes-acceso/mia` | autenticado | — | 200 `Solicitud` | 401, 404 `no_encontrado` |
| `GET /solicitudes-acceso?estado=pendiente` | administrador | — | 200 `[Solicitud]` | 401, 403 `sin_permiso` |
| `POST /solicitudes-acceso/{id}/aprobar` | administrador | `{rol: "personal"\|"administrador", especialidad}` | 200 `Solicitud` | 401, 403, 404, 409 (no pendiente), 422 |
| `POST /solicitudes-acceso/{id}/rechazar` | administrador | `{motivo}` | 200 `Solicitud` | 401, 403, 404, 409, 422 |
| `GET /usuarios?rol=` | administrador | — | 200 `[Perfil]` | 401, 403 |
| `PATCH /usuarios/{id}` | administrador | `{rol?, especialidad?}` | 200 `Perfil` | 401, 403, 404, 409 `ultimo_administrador`, 422 |

- `Perfil`: `{id, correo, correo_confirmado, nombre, telefono, nombre_artistico, rol, especialidad}` (`null` donde no aplique).
- `Solicitud`: `{id, id_usuario, nombre, correo, especialidad, mensaje, estado: "pendiente"|"aprobada"|"rechazada", motivo, creada_en, revisada_en}`.
- Verificación del correo: Supabase local no permite iniciar sesión con el correo sin confirmar, así que Supabase lo da por confirmado al registrarse y la verificación se lleva en `usuario.correo_verificado_en` ([ADR-008](../00-proyecto/decisiones/ADR-008-acceso-y-roles-v1.md)). El frontend pide el enlace con `signInWithOtp` (redirección a `/app/perfil?verificar=1`) y llama a `POST /perfil/verificar-correo`; el backend lo acepta solo si el método de la sesión (`amr` del token) es `otp`/`magiclink` u `oauth`.
- `correo` de otros usuarios (bandeja y lista del Administrador) se lee con `public.correo_de_usuario(id)` (`security definer`: el propio usuario o un administrador), porque vive en `auth.users`.
- `telefono`: dígitos con `+` inicial opcional, de 9 a 15 dígitos. `especialidad`: texto libre corto (la lista cerrada llega con RF-07).
